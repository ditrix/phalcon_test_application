# 1. Rules для Cursor (постоянные правила)

**Как использовать:** создайте файл `.cursor/rules/project.mdc`, вставьте в него содержимое блока ниже (вместе с frontmatter). Эти правила будут подключаться ко всем чатам автоматически. Подробности проекта лежат в `AGENTS.md` в корне репозитория.

Порядок работы: промпты `2-prompt-...` → `9-prompt-...` выполняются **строго по очереди**, каждый в **новом чате** Cursor. Следующий шаг начинайте только когда проверка предыдущего прошла.

```md
---
description: Правила проекта Phalcon 3 импорт заявок
alwaysApply: true
---

# Язык
- Общайся со мной по-русски. Код, комментарии, имена, коммиты, README-код — на английском.
- Я Laravel-разработчик, Phalcon знаю слабо. Если Phalcon работает не так, как Laravel, кратко объясни разницу (1-2 предложения).

# Обязательно перед работой
- Прочитай `AGENTS.md` в корне. Он главный источник правды по стеку, схеме БД, правилам импорта.
- Если инструкция из чата противоречит AGENTS.md — остановись и спроси.

# Жёсткие ограничения стека
- PHP 7.2.34: без typed properties, arrow functions (`fn`), `??=`, `match`, union types, named arguments, `str_contains`, `str_starts_with`.
- Phalcon 3.4 (C-расширение). НЕ Phalcon 4/5. Документация только 3.4: https://docs.phalcon.io/3.4/en/
- MySQL 5.7, strict mode включён.
- Не добавляй composer-зависимости без моего согласия. Предпочтение — ноль зависимостей.
- Никогда не используй `set_time_limit()` и `ini_set('max_execution_time')`. Лимит 30 секунд — часть задания.

# Phalcon: не выдумывай API
- Если не уверен, что класс или метод существует в Phalcon 3.4, скажи «не проверено» и проверь командой в контейнере, например:
  `docker compose exec web php -r 'var_dump(method_exists("Phalcon\\Http\\Request","getUploadedFiles"));'`
- Не копируй примеры из документации Phalcon 4/5.
- Не применяй привычки Laravel: нет Eloquent, нет helper-функций `request()`/`response()`, нет Blade, нет artisan, `.env` не загружается автоматически (используй `getenv()`).
- В цикле импорта не используй ORM (`Phalcon\Mvc\Model`), только сырой SQL через `$db->execute()`.

# Стиль работы
- Маленькие вертикальные шаги. Сначала короткий план (5-8 строк), потом код.
- После каждого изменения давай точную команду для проверки (`docker compose exec ...`) и ожидаемый результат.
- Не трогай код, не относящийся к текущему шагу. Не добавляй фичи, которых нет в AGENTS.md.
- Схему БД меняй только новым файлом в `migrations/` и явно сообщай об этом.
- Если требование неоднозначное — задай ОДИН конкретный вопрос вместо догадок.
- Не оставляй TODO без объяснения и не пиши заглушки, которые выглядят рабочими.

# Качество кода
- Контроллеры тонкие, логика в `app/Services`. Чистые функции (нормализация) без доступа к БД и Phalcon.
- PSR-4 автозагрузка (`App\` → `app/`), PSR-12.
- Вывод в HTML всегда экранируется (в данных произвольный текст).
- Ошибки не глотать молча: считать и показывать в статистике.

# Формат ответа после шага
1. Что сделано (список файлов).
2. Как проверить (команды).
3. Что может пойти не так / что я не смог проверить.
4. Что делать дальше (название следующего промпта).
```
